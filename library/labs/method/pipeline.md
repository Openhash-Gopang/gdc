# GDC 테스트 파이프라인 — 소유권·순서·파일 규약 (설계안)

klaw의 `pipeline.md` 를 기준으로 한 설계안이다. P1~P2에서 실제 스크립트를 만들면서 이 문서를 확정한다.
현재(P0) 구현된 스크립트는 없다.

## 1. 3단계

```
(1) 실행     시나리오를 입력해 신용평가·기업가치·상품 거래 결과를 생성
(2) 독립 검수  (1)의 결과 전문을 다른 모델/세션이 사후 검수 (같은 모델의 에코 챔버 방지)
(3) 재검토    (2)의 검수 보고서에 항목별 수용/반박을 강제하고 최종 결과를 다시 작성
```

세 단계는 API 키 격리와 단계별 재개를 위해 합치지 않는다. 키는 코드·커밋·로그에 남기지 않는다.

## 2. 최종 결과의 소유권

같은 이름의 결과 파일이 단계에 따라 다른 디렉터리에 생길 수 있으므로 디렉터리로 구분한다.
검수까지 거친 시나리오는 가장 나중 단계(재검토) 디렉터리의 결과를 권위 있는 결과로 취급한다.

## 3. 디렉터리 규약 (예정)

```
rounds/<R>/                  (1) 실행 산출물: <scenario_id>.json, results.csv
rounds/<R>-check/            (2) 독립 검수 보고서
rounds/<R>-final/            (3) 재검토 후 최종 결과
```

## 4. 방법론 버전 관리

방법론 본체와 검수 SP는 같은 파일명·버전 표기·자동 탐지 규칙을 쓴다
(`gdc_credit_v1_0.md`, `gdc_check_v1_0.md` 처럼 루트에 두고 가장 높은 버전을 채택).
두 파일의 버전 숫자는 서로 다른 의미이므로 비교하지 않는다.

## 5. 실제 잔액 거래 시나리오의 추가 규칙

- 실행 전 대상 계정이 테스터 allowlist에 있는지 서버 쪽에서 확인한다.
- 실행 기록에는 거래 해시와 PDV 기록 ID를 남긴다.
- 시나리오 실패로 잔액이 어긋나면 보정 거래로 맞추고, 보정 사유를 `note` 에 남긴다.
