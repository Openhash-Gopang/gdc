# 적금(정액 적립) 상품 명세 v0.1 (2026-10-03, P3a)

GDC 필드테스트의 적금 상품 규칙이다. **시뮬레이션용 명세**이며 서버에는 아직 없다. 이 문서의 값은 모두 **GDC 설계값**이고
외부 상품에서 가져온 참고값이 아니다. 한도 명세([limits_v0_1.md](limits_v0_1.md))와 같은 면책이 적용된다 — 상용 금융 서비스가 아니고,
인허가를 대체하지 않는다. 금액 단위는 GDC(₮), 1₮ = KRW 1,000.

## 0. 현재 승인 범위와의 관계 (먼저 읽을 것)

- `js/gdc-bank.js`는 **예금 이자 지급을 LEGAL-HOLD로 막아 두었다**(정산 파이프라인 F: 대출수익 − 서버비용 = 예금이자 재원이 구축되기 전까지 무이자 보관만 라이브).
  적금의 이자도 같은 문제다. 그래서 **이 명세의 기본 약정 이율은 0(무이자 보관)** 이고, 이율이 0보다 큰 계약은 **시뮬레이션에서만** 다룬다.
- 이율 > 0 인 적금을 실제 잔액으로 지급하려면 이자 재원을 먼저 정해야 한다(미결정). 이 명세는 그 결정을 대신하지 않는다.
- 적금 납입은 사용자 → 예금금고(`gdc-deposit-vault`)로 가는 이체이므로 **납입마다 이체 한도(limits_v0_1 §2)를 받는다** (§6).

## 1. 계약 입력

| 필드 | 값 | 설명 |
|------|----|------|
| `monthlyAmount` | 정수 100 이상 1000 이하 (₮) | 월 납입액. 상한은 1회 이체 상한(₮1,000)과 같다. 하한은 GDC 설계값 |
| `termMonths` | 6 또는 12 | 약정 기간(개월). 필드테스트 범위의 GDC 설계값 |
| `rateBp` | 정수 0 이상 50 이하 | 연 약정 이율(bp, 1bp = 0.01%). 필수 입력이며(생략하면 `RATE_INVALID`) 현행 승인 범위의 값은 0. 상한 50bp(0.5%)는 신용평가 최상위 등급 대출 금리(연 0.5%)를 넘지 않도록 한 GDC 설계값 |
| `outcomes` | 배열, 원소는 `"paid"` 또는 `"missed"` | 1회차부터 차례로, 각 달 납입일의 결과. `outcomes[k]`는 1부터 센 k번째 달이다(배열 인덱스로는 k−1) |
| `cancelAt` | 선택, 정수 1 이상 | 해당 달 납입 결과를 반영한 **직후** 사용자가 해지하는 시점(달 번호). 필드가 없거나 `null`이면 해지 없음 |

"정수"는 값이 정수이면 된다(JSON의 `500.0`은 정수 500). `outcomes`의 형식 검사는 계약이 중간에 끝나 읽지 않게 되는 뒷 달의 원소까지 포함해 배열 전체에 적용한다.

입력이 아래 조건을 어기면 계산하지 않고 오류 코드를 돌려준다. 검사 순서는 `monthlyAmount` → `termMonths` → `rateBp` → `outcomes` → `cancelAt`.

| 오류 코드 | 조건 |
|-----------|------|
| `AMOUNT_INVALID` | `monthlyAmount`가 정수가 아니거나 범위 밖 |
| `TERM_INVALID` | `termMonths`가 6, 12가 아님 |
| `RATE_INVALID` | `rateBp`가 정수가 아니거나 범위 밖 |
| `OUTCOMES_INVALID` | `outcomes`가 배열이 아니거나, 원소가 `paid`/`missed`가 아니거나, 길이가 `termMonths`보다 큼 |
| `CANCEL_INVALID` | `cancelAt`이 정수가 아니거나 1 미만이거나 `termMonths` 초과이거나, `outcomes` 길이보다 큼 |

## 2. 달의 진행

달 번호 k는 1부터 시작하고 1회차 납입일이 1이다. 달 k를 처리할 때:

1. `outcomes[k]`가 `paid`이면 월 납입액이 적립된다(납입한 달 목록에 k를 더한다). `missed`이면 아무것도 적립되지 않는다. **미납분의 추후 납입(후납)과 미리 내는 선납은 허용하지 않는다.**
2. `outcomes[k]`가 `missed`이고 `outcomes[k-1]`도 `missed`이면(2회 **연속** 미납) 계약은 이 달 끝에 **자동 해지**된다 (상태 `auto_terminated`, §4의 중도해지 계산을 t = k로 적용). k = 1 이면 직전 달이 없으므로 연속 미납이 아니다. 만기 달(k = `termMonths`)에 2회 연속 미납이 성립해도 자동 해지이며 만기가 아니다.
3. 자동 해지가 아니고 `cancelAt == k`이면 이 달 끝에 사용자 **해지**된다 (상태 `cancelled`, 중도해지 계산을 t = k로 적용).
4. 위에 해당하지 않고 k == `termMonths`이면 **만기**다 (상태 `matured`, §3).
5. 그 외에는 다음 달로 간다. `outcomes`가 끝났는데 끝나지 않았으면 상태는 `active`이고 지급액은 없다.

자동 해지와 사용자 해지가 같은 달에 겹치면 자동 해지가 먼저다. 만기 달에 `cancelAt == termMonths`이면 만기로 본다(해지 아님).
한 번 끝난 계약은 이후 달의 결과를 읽지 않는다. 자동 해지가 `cancelAt`보다 앞선 달에 일어나면 `cancelAt`은 무시한다. `cancelAt`이 `outcomes` 길이보다 크면(만기 달 포함) `CANCEL_INVALID`다.

## 3. 만기 지급

- **원금** = 납입한 달의 수 × `monthlyAmount`.
- **이자 기준합** S = 납입한 달 j마다 `monthlyAmount × rateBp × (termMonths − j + 1)`의 합. (정액적립식 단리: 달 j에 낸 돈은 만기까지 `termMonths − j + 1`개월 맡겨진다.)
- **이자** = S ÷ 1200 의 몫(버림)을 100으로 나눈 값(₮, 소수 둘째 자리, 0.01₮ 단위 미만 버림). 즉 `이자_센트 = floor(S / 1200)`, `이자 = 이자_센트 / 100`.
  (연 이율 = rateBp/10000, 개월은 1/12년 → 이자 = Σ 납입액 × rateBp/10000 × 개월/12. ₮ 소수 둘째 자리 단위로 환산하면 S/1200 이다.)
- **지급액** = 원금 + 이자.

## 4. 중도해지·자동 해지 지급

t는 해지가 일어난 달 번호(해당 달 결과를 반영한 직후)이다. 원금은 **전액 돌려준다.**

- 납입한 달 j마다 맡겨진 개월 수는 `t − j + 1`이다 (달 j 납입일에 맡겨 달 t 끝에 찾는다).
- **이자 기준합** S' = 납입한 달 j마다 `monthlyAmount × rateBp × (t − j + 1)`의 합.
- **중도해지 이율은 약정 이율의 50%** 다 (GDC 설계값). 그래서 `이자_센트 = floor(S' / 2400)`, 이자 = 이자_센트 / 100.
- 지급액 = 원금 + 이자. 해지에 위약금은 없다.

## 5. 출력

| 필드 | 설명 |
|------|------|
| `status` | `matured` / `cancelled` / `auto_terminated` / `active` |
| `endMonth` | 계약이 끝난 달 번호 (`active`면 처리한 마지막 달 번호, `outcomes`가 비어 있으면 0) |
| `paidCount` | 납입한 달의 수 |
| `principal` | 원금(₮) = 납입한 달의 수 × 월 납입액. `active`이면 그때까지 낸 원금 |
| `interest` | 이자(₮, 소수 둘째 자리). `active`이면 0 |
| `payout` | 지급액(₮). `active`이면 `null` |

## 6. 한도와의 관계 (이 명세가 계산하지 않는 것)

- 납입은 `/biz/order`(items 빈 이체)이므로 필드테스터는 한도를 받는다: 1회 ₮1,000(`monthlyAmount` 상한과 같음), 1일 유출 ₮2,000(다른 이체·예치·상환과 합산),
  수취인이 예금금고라 "처음 보내는 수취인" 한도는 받지 않는다(hondi #515가 예금금고를 제외한다).
- 따라서 같은 날 다른 유출이 많아 납입이 한도에 걸리면 그 달은 `missed`와 같이 취급해야 하는데, **이 규칙은 서버 이식 때 정한다**(미결정). 이 명세의 `outcomes`는 이미 결정된 결과를 입력으로 받는다.
- 금고에서 사용자에게 돌려주는 지급(만기·해지)은 들어오는 거래이므로 한도 대상이 아니다.

## 7. 알려진 한계

1. 값(월 납입액 하한 ₮100, 상한 50bp, 중도해지율 50%, 연속 2회 미납 해지)은 모두 GDC 설계값이며 근거 자료가 없다.
2. 이율 > 0 의 이자 재원이 정해지지 않았다(§0). 서버에 올리지 않는다.
3. 납입일·휴일·시간대는 다루지 않는다. 달 번호만 있다.
4. 한도로 납입이 거절된 달의 처리(§6)가 미결정이다.
5. 서버 스키마(`gdc_test_savings` 등)와 엔드포인트가 없다. 이 명세는 시뮬레이터(`js/gdc-savings.js`)와 라운드 3 시나리오로만 검증된다.
6. 검증 이력: 라운드 3(`rounds/r03`), 독립 검수 `rounds/r03-check`, 재검토 `rounds/r03-final` — 같은 제작사의 다른 모델이 한 검수이며 제3자 검증은 아니다.
