# GDC 필드테스트 한도 명세 v0.1 (2026-10-03, 서버 반영 상태 갱신 2026-10-03)

실제 GDC 잔액이 움직이는 거래를 필드테스터 계정에서 시험하기 위한 한도 규칙이다.
이 문서가 명세이고, `js/gdc-limits.js` 는 이 명세의 실행 가능한 기준 구현이다.
금액 단위는 GDC(₮)이며 런칭 기준가는 1₮ = KRW 1,000이다.

**이 명세가 하는 일과 하지 않는 일**
- 한다: 한도 값과 그 근거, 검사 순서, 경계 규칙, 서버 이식 요건을 정한다.
- 하지 않는다: 이 저장소는 한도를 강제하지 않는다. 강제는 서버(`worker.js`, 별도 저장소 Openhash-Gopang/hondi)가 한다. 반영 상태(2026-10-03): **대출 신청 한도**는 hondi #514, **테스터 계정의 이체·예치 한도**는 hondi #515로 main에 병합됐다(병합 후 production 배포는 deploy-worker 워크플로 기준). 클라이언트(`js/gdc-core.js`의 `transfer()` 등)에는 사전 검사가 연결되어 있지 않다 — 서버가 거절하면 웹앱이 서버의 `detail` 문구를 경고창으로 보여준다.
- 이 명세는 법률 자문이 아니다. 인허가가 필요한 업무를 대체하지 않으며, 일반 이용자 확대 전에는 별도 법률 검토가 필요하다.

- "GDC 설계값"은 근거 자료에서 도출한 값이 아니라 필드테스트를 위해 보수적으로 정한 값이다. 필드테스트 결과로 조정한다. 이 값을 규제 기준이라고 서술하지 않는다.
- 지연이체(최소 3시간)는 보류 상태를 가진 거래 모델이 필요해서 P3로 미룬다. 1억원 이상 지연인출은 GDC 한도가 훨씬 낮아 해당하지 않는다.

## 3. 정의

- **유출**: 사용자 지갑에서 나가는 거래의 합. 이체, 예치(`openDeposit`), 대출 상환(`repayLoan`)을 포함하고, P3 이후 보험료·증권 매수를 포함한다. 대출 실행금과 예치 해지금처럼 들어오는 거래는 포함하지 않는다.
- **1일**: 한국 표준시(KST) 달력일 00:00~24:00. 롤링 24시간이 아니다.
- **처음 보내는 수취인**: 해당 사용자가 그 수취인에게 완료된 거래를 한 번도 하지 않은 경우.
- **연 소득**: 필드테스트에서는 재무제표의 영업이익(`pl_revenue - pl_cogs - pl_opex`)을 쓴다. 0 이하이면 `NO_INCOME`이다.
- **연 원리금 상환액**: 원리금균등, 만기 12개월 가정, 연이율 = 등급 금리 + 스트레스 가산금리. 서버에는 기존 대출의 상환 일정이 없어, 서버 구현은 활성 대출의 미상환 원금(`outstanding_principal`)을 같은 가정(12개월, 대출 시점의 `annual_rate` + 가산금리)으로 환산해 기존 연 상환액에 더한다. 기준 구현(`checkLoan`)은 이 값을 호출자가 넘기게 두었다. 두 구현의 검사 순서와 결과 코드는 같고, 시나리오 11건으로 일치를 대조한다.
- **보정 거래**: 오입력·사고를 바로잡는 운영자 서명 거래이며 사용자 한도에 산입하지 않는다. 삭제나 롤백은 하지 않는다(원장 불변성).

## 4. 검사 순서와 경계

경계값은 포함한다(상한과 같으면 통과).

**유출 거래** (`checkTransfer`): 금액 유효성 → 1회 상한 → 신규 수취인 상한 → 1일 누적 상한.
**대출** (`checkLoan`): 금액 유효성 → 1건 상한 → 잔액 합계 상한 → 순자산 비율 → 소득 유무 → DSR.

금액 유효성은 "0보다 큰 유한한 number"이며, 문자열 숫자는 거부한다.

| 코드 | 의미 |
|------|------|
| `OK` | 통과 |
| `AMOUNT_INVALID` | 금액 형식 오류 |
| `PER_TX_LIMIT` | 1회 상한 초과 |
| `NEW_RECIPIENT_LIMIT` | 처음 보내는 수취인 상한 초과 |
| `DAILY_LIMIT` | 1일 유출 합계 초과 |
| `LOAN_PER_LIMIT` / `LOAN_TOTAL_LIMIT` / `LOAN_EQUITY_LIMIT` | 대출 1건 / 잔액 합계 / 순자산 비율 초과 |
| `NO_INCOME` | 소득 0 이하 |
| `DSR_EXCEEDED` | DSR 40% 초과 |

## 5. 강제 요건 (서버)

1. 모든 한도는 서버가 검사한다. 클라이언트 검사는 사용성용이다.
2. 테스터 allowlist(`gdc_test_financial_statements` 레코드 존재)로 한도 대상을 정한다. 이체·예치는 `/biz/order`를 지나는데 이 경로는 K-Market 결제와 공용이므로, **`tx.items`가 비어 있는 거래이면서 보내는 계정(`tx.input.owner_guid`)이 테스터일 때만** 한도를 적용한다. 일반 회원의 이체·예치와 카탈로그 구매에는 한도가 없다(2026-10-03 결정: 테스터 계정 한정). 테스터 여부나 이력을 확인하지 못하면 거절한다(fail-closed).
3. 1일 누적은 서버 원장에서 계산한다. 클라이언트가 보낸 값을 믿지 않는다.
4. 한도 거부는 사유 코드와 함께 PDV에 기록한다. **미구현** — 서버는 지금 `console.warn`만 남긴다.
5. 한도 값은 코드에 박지 않고 설정으로 둔다. 이 저장소의 `LIMITS` 상수가 기본값이다.

## 6. 이식 계획과 진행 (이 저장소 밖)

서버(`worker.js`)는 별도 저장소(hondi-proxy)에 있고 main 보호 브랜치 규칙이 적용된다. 이식은 다음 순서로 한다.

1. ✅ `js/gdc-limits.js`의 로직과 `LIMITS`를 서버에 옮긴다 — 대출 한도(`_gdcCheckLoanLimits`, #514), 이체·예치 한도(`_gdcCheckTransferLimits`, #515).
2. ✅ `library/labs/rounds/r01/scenarios.json`의 `transfer`, `loan_limit` 시나리오를 서버 구현의 회귀 테스트로 쓴다 — hondi `test/fixtures/`에 사본이 있다. 이 저장소의 시나리오를 바꾸면 사본도 함께 바꿔야 한다.
3. 서버 구현이 같은 시나리오를 통과했다. 클라이언트 사전 검사(`gdc-core.js`/`gdc-bank.js`)는 아직 연결하지 않았다.
4. 미완: 한도 값을 설정으로 빼기(§5-5), PDV 기록(§5-4), 동시 요청 경쟁 상태 방지.

## 7. 알려진 한계

- 위 한도 값 중 "GDC 설계값"은 근거가 약하다. 1차 법령 확인과 필드테스터 의견으로 조정한다.
- 대출 만기와 상환 일정이 서버 스키마에 없다. DSR은 12개월 가정으로 계산한다.
- 신규 수취인과 1일 유출은 서버가 `blocks`에서 `buyer_guid`가 보내는 계정이고 `block_type`이 `ai_usage_charge`가 아닌 최근 200건을 읽어 계산한다. 이체 블록의 `block_type` 값을 hondi 저장소에서 확인하지 못해 이렇게 넓게 집계하며, 예치도 유출에 들어간다. 이력이 200건을 넘고 조회분 전체가 오늘이면 거절한다.
- 한도 검사와 L1 기록 사이에 경쟁 상태가 있다. 동시에 두 요청이 각각 통과하면 합계 한도를 넘길 수 있다(대출 잔액 합계도 같다). 필드테스트 규모에서 낮은 위험으로 보았으며, 예약 후 지급(reserve-then-disburse) 패턴으로 후속 보강이 필요하다.
- **미결정 — 대출 상환이 한도를 받는다.** §3은 대출 상환을 유출에 포함한다. `repayLoan()`은 `transfer()`로 대출금고에 보내므로 같은 `/biz/order`를 지나 1회 ₮1,000·1일 ₮2,000 한도를 받는다. 대출 1건 상한이 ₮3,000이라 한 번에 갚을 수 없는 금액이 생긴다(나눠 갚으면 된다). 상환을 한도에서 제외할지 정해야 한다. **추가 관찰(2026-10-03)**: 서버는 예금금고만 "처음 보내는 수취인" 판정에서 제외한다. 대출금고는 제외되지 않으므로, 테스터가 대출금고로 처음 보내는 상환은 1회 ₮100을 넘으면 `NEW_RECIPIENT_LIMIT`으로 거절된다(이후 상환은 ₮1,000까지).
- 웹앱의 대출 신청과 신용평가 화면은 LEGAL-HOLD(2026-07-18)로 막혀 있다. 서버 대출 한도는 반영됐지만 웹앱에서는 실행할 수 없고, 그 해제는 이 명세의 범위 밖이다.
- 영업이익을 연 소득 대용으로 쓰는 것은 개인 사용자에게 어색하다. P2에서 소득 항목을 정한다.
