# GDC 필드테스트 한도 명세 v0.1 (2026-10-03)

실제 GDC 잔액이 움직이는 거래를 필드테스터 계정에서 시험하기 위한 한도 규칙이다.
이 문서가 명세이고, `js/gdc-limits.js` 는 이 명세의 실행 가능한 기준 구현이다.
금액 단위는 GDC(₮)이며 런칭 기준가는 1₮ = KRW 1,000이다.

**이 명세가 하는 일과 하지 않는 일**
- 한다: 한도 값과 그 근거, 검사 순서, 경계 규칙, 서버 이식 요건을 정한다.
- 하지 않는다: 한도를 강제하지 않는다. 2026-10-03 현재 어떤 한도도 실제로 적용되지 않는다. `transfer()`(js/gdc-core.js)는 금액 상한 검사가 없고, 서버(`worker.js`, 별도 저장소) 쪽 한도 검사 여부는 이 저장소에서 확인할 수 없다.
- 이 명세는 법률 자문이 아니다. 인허가가 필요한 업무를 대체하지 않으며, 일반 이용자 확대 전에는 별도 법률 검토가 필요하다.

- "GDC 설계값"은 근거 자료에서 도출한 값이 아니라 필드테스트를 위해 보수적으로 정한 값이다. 필드테스트 결과로 조정한다. 이 값을 규제 기준이라고 서술하지 않는다.
- 지연이체(최소 3시간)는 보류 상태를 가진 거래 모델이 필요해서 P3로 미룬다. 1억원 이상 지연인출은 GDC 한도가 훨씬 낮아 해당하지 않는다.

## 3. 정의

- **유출**: 사용자 지갑에서 나가는 거래의 합. 이체, 예치(`openDeposit`), 대출 상환(`repayLoan`)을 포함하고, P3 이후 보험료·증권 매수를 포함한다. 대출 실행금과 예치 해지금처럼 들어오는 거래는 포함하지 않는다.
- **1일**: 한국 표준시(KST) 달력일 00:00~24:00. 롤링 24시간이 아니다.
- **처음 보내는 수취인**: 해당 사용자가 그 수취인에게 완료된 거래를 한 번도 하지 않은 경우.
- **연 소득**: 필드테스트에서는 재무제표의 영업이익(`pl_revenue - pl_cogs - pl_opex`)을 쓴다. 0 이하이면 `NO_INCOME`이다.
- **연 원리금 상환액**: 원리금균등, 만기 12개월 가정, 연이율 = 등급 금리 + 스트레스 가산금리. 기존 대출의 상환 일정 데이터가 서버에 없어 기존 상환액은 호출자가 넘기는 값(기본 0)이다. 이 점이 현재 한계다.
- **보정 거래**: 오입력·사고를 바로잡는 운영자 서명 거래이며 사용자 한도에 산입하지 않는다. 삭제나 롤백은 하지 않는다(원장 불변성).

## 4. 검사 순서와 경계

경계값은 포함한다(상한과 같으면 통과).

**유출 거래** (`checkTransfer`): 금액 유효성 → 1회 상한 → 신규 수취인 상한 → 1일 누적 상한.
**대출** (`checkLoan`): 금액 유효성 → 1건 상한 → 잔액 합계 상한 → 순자산 비율 → 소득 유무 → DSR.

금액 유효성은 "0보다 큰 유한한 number"이며, 문자열 숫자는 거부한다.

| 코드 | 의미 |
|------|------|
| `OK` | 통과 |
| `AMOUNT_INVALID` | 금액 형식 오류 |
| `PER_TX_LIMIT` | 1회 상한 초과 |
| `NEW_RECIPIENT_LIMIT` | 처음 보내는 수취인 상한 초과 |
| `DAILY_LIMIT` | 1일 유출 합계 초과 |
| `LOAN_PER_LIMIT` / `LOAN_TOTAL_LIMIT` / `LOAN_EQUITY_LIMIT` | 대출 1건 / 잔액 합계 / 순자산 비율 초과 |
| `NO_INCOME` | 소득 0 이하 |
| `DSR_EXCEEDED` | DSR 40% 초과 |

## 5. 강제 요건 (서버)

1. 모든 한도는 서버가 검사한다. 클라이언트 검사는 사용성용이다.
2. 테스터 allowlist(`gdc_test_financial_statements` 레코드 존재)를 서버가 모든 잔액 이동 요청에서 확인한다. 현재는 신용평가·대출 신청 경로에서만 확인되는 것으로 코드 주석에 적혀 있으며, 이체·예치 경로는 확인하지 못했다.
3. 1일 누적은 서버 원장에서 계산한다. 클라이언트가 보낸 값을 믿지 않는다.
4. 한도 거부는 사유 코드와 함께 PDV에 기록한다.
5. 한도 값은 코드에 박지 않고 설정으로 둔다. 이 저장소의 `LIMITS` 상수가 기본값이다.

## 6. 이식 계획 (이 저장소 밖)

서버(`worker.js`)는 별도 저장소(hondi-proxy)에 있고 main 보호 브랜치 규칙이 적용된다. 이식은 다음 순서로 한다.

1. `js/gdc-limits.js`의 로직과 `LIMITS`를 서버에 옮긴다.
2. `library/labs/rounds/r01/scenarios.json`의 `transfer`, `loan_limit` 시나리오를 서버 구현의 회귀 테스트로 쓴다.
3. 서버 구현이 같은 시나리오를 통과한 뒤에야 `gdc-core.js`/`gdc-bank.js`에 클라이언트 사전 검사를 연결한다.
4. 그 전에는 한도가 강제되지 않는다는 점을 사이트와 문서에 숨기지 않는다.

## 7. 알려진 한계

- 위 한도 값 중 "GDC 설계값"은 근거가 약하다. 1차 법령 확인과 필드테스터 의견으로 조정한다.
- 대출 만기와 상환 일정이 서버 스키마에 없다. DSR은 12개월 가정으로 계산한다.
- 신규 수취인 판정 데이터(과거 거래 상대 목록)의 서버 쪽 출처가 정해지지 않았다.
- 영업이익을 연 소득 대용으로 쓰는 것은 개인 사용자에게 어색하다. P2에서 소득 항목을 정한다.
