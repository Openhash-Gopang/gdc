# GDC 필드테스트 — 방법론·시나리오·라운드

klaw의 `library/benchmark/` 에 대응하는 폴더다. 은행(예금·적금·대출), 보험, 증권, 디지털 화폐
기능을 시나리오로 시험하고, 신용평가·기업가치 평가 방법론을 라운드마다 갱신·검증하는
절차를 기록한다.

**상태 (2026-10-03)**: 한도 명세 v0.1과 라운드 1(기준선, 시뮬레이션)이 있고, 한도는 서버에 반영됐다(대출·테스터 이체·예치).
라운드 1 결과는 [rounds/r01/results.md](rounds/r01/results.md). 독립 검수(파이프라인 2단계)는 아직 하지 않았다.

**면책**: GDC는 고팡 플랫폼 안의 결제·저축·대출 단위이며, 이 테스트는 은행업·보험업·금융투자업
등 인허가를 대체하지 않는다. 여기 수록되는 데이터는 자체 실험 결과이며 제3자 검증을 거치지
않았다. 특허 출원 명세서의 처리 속도·정확도 수치는 검증되지 않은 값이므로 어디에도 옮기지 않는다
(로드맵 v1.2 §0 원칙 유지). "특허 출원" · "특허 등록" · "실제 구현"을 섞어 쓰지 않는다.

## 0. 테스트 범위와 가드 (2026-10-03 결정)

| 항목 | 결정 |
|------|------|
| 거래 범위 | 실제 GDC 잔액이 움직이는 거래까지 포함한다 (예금·적금·대출·보험료/보험금·증권 거래) |
| 대상 계정 | 현직 금융기관 종사자 필드테스터에 한정한다 (`gdc_test_*` 레코드가 있는 계정만). 일반 이용자에게 노출하지 않는다 |
| 확대 | 일반 이용자 확대는 이 결정의 범위 밖이다. 별도 법률 자문과 인허가 검토가 먼저 필요하다 |
| 표기 | 모든 상품 컬렉션은 `gdc_test_` 접두어를 쓰고, 모든 페이지에 필드테스트 안내를 둔다 |

실제 잔액이 움직이므로 아래 요건을 서버가 강제하는 것을 확인한 뒤에야 해당 상품을 연다.
**한도 값과 근거는 [method/limits_v0_1.md](method/limits_v0_1.md)에 있다 (P1, 2026-10-03).
서버(hondi 저장소 `worker.js`)에는 대출 신청 한도와 테스터 계정의 이체·예치 한도가 반영됐다** (명세 §6).
이 저장소의 `js/gdc-limits.js`는 기준 구현일 뿐 클라이언트에 연결되어 있지 않다.

- 모든 거래에 ED25519 서명을 요구하고 PDV에 6하 원칙으로 기록한다.
- 1회·1일·신규 수취인·대출 한도를 둔다 (값은 명세 §2, 대부분 근거가 약한 GDC 설계값이다).
- 오입력 거래는 삭제·롤백하지 않고 보정 거래로 상쇄한다 (원장 불변성).
- 테스터 allowlist(`gdc_test_*` 레코드 존재 여부)를 서버 쪽에서 검사한다. 브라우저 쪽 검사에 의존하지 않는다.
- 상품별로 "되돌릴 수 없는 거래"와 "시뮬레이션 거래"를 화면에서 구분해 표시한다 (미구현).

## 1. 전체 구조

```
시나리오 매트릭스 작성(상품별)
   -> 라운드 N: 그 시점의 방법론으로 표본 밖 시나리오 실행 -> 기대 결과와 대조
   -> 오류 분석 -> 방법론 패치안 작성(같은 유형 오류 2회 이상 또는 구조적 결함일 때만 갱신)
   -> 라운드 N+1 ...
```

핵심 원칙은 klaw와 같다. **각 라운드의 결과는 그 라운드 시작 시점의 방법론으로, 아직 보지 않은
시나리오에 대해 얻는다.** 방법론을 특정 시나리오에 맞추는 과적합을 구조적으로 제한하기 위해서다.
임의 규칙 추가는 금지한다.

## 3. 알려진 한계 · 미해결 항목 (P1 시점)

**해결됨 (P1)**
- 기존 테스트 3건 실패를 정리했다 (36건 중 33 통과 -> 49건 중 48 통과, 실패 0, todo 1).
  - `activated_features.test.mjs` 2건은 2026-07-18 LEGAL-HOLD 상태를 단언하고 있었다.
    2026-09-06 필드테스트 승인 범위(대출·신용평가는 필드테스터 한정, 예금 이자 지급은 보류)에 맞게 다시 썼다.
    `evaluateCredit()`가 필드테스터가 아니면 값을 돌려주지 않고 `TESTER_ONLY`로 실패한다는 단언은 유지했다.
  - `src_gdc.test.mjs`의 변동성 테스트는 약화하지 않고 `todo`로 표시했다. `smartVault.js` 주석은 안정형
    "변동성<5%"인데 값은 정확히 0.05다. 표기와 값 중 무엇이 맞는지는 이 파일이 LEGAL-HOLD(미배선)라
    결정하지 않았다. 별도로 "5% 이하" 단언을 추가했다.

**미해결**
1. **한도는 서버에만 있고 테스터 계정에만 적용된다.** `js/gdc-limits.js`는 기준 구현일 뿐 `transfer()`/`openDeposit()`에
   연결되어 있지 않다. 일반 회원의 이체·예치에는 한도가 없다. 동시 요청 경쟁 상태, PDV 기록, 대출 상환이 이체 한도를
   받는 문제는 미해결이다 (명세 §7).
2. **한도 값 대부분이 GDC 설계값이다.** 근거 자료는 2차 자료이며 1차 법령으로 확인하지 못했다 (명세 §1~§2).
3. **대출 만기·상환 일정이 서버 스키마에 없다.** DSR은 12개월 가정으로 계산하고, 서버는 활성 대출의 미상환 원금에서 기존 상환액을 같은 가정으로 환산한다.
4. **신용평가 관찰 사항** (R01에서 드러났고 지금은 기대대로 동작하지만 정책 판단이 필요하다):
   - 부채가 0이고 순자산이 양수면 부채비율 100점인데, 순자산이 0이면 중립 50점이다 (cred-006, cred-010).
   - 영업손실 -20%여도 다른 지표가 좋으면 A 등급이 나온다 (cred-007).
   - 개인에게 영업이익을 연 소득 대용으로 쓰는 것은 어색하다.
5. **`README.md` §5의 대출·신용평가 스펙이 현행 코드와 다르다.** README는 금리 2.0~8.0%·점수 구간을 적고,
   코드와 사이트(desktop.html)는 AAA 연 0.5%대 ~ C 연 5%대다. 사이트와 코드가 일치하므로 README가 낡은 것으로
   보이지만 확정하지 않았다 (P2에서 신용평가 방법론을 문서로 고정하며 정리한다).
6. R01의 `transfer`·`loan_limit` 통과는 **새로 만든 기준 구현이 같은 사람이 쓴 명세와 일치한다**는 뜻일 뿐,
   독립 검증이 아니다. 실제 의미는 서버 이식 후 같은 시나리오를 통과할 때 생긴다.
   `credit` 시나리오는 기존 코드를 손계산 기대값과 대조한 것이라 상대적으로 의미가 있으나 역시 독립 검수 전이다.
7. 보험·증권·적금·기업가치 평가는 코드·스키마·문서가 아직 없다 (P2~P3). `src/gdc/smartVault.js`는
   집합투자기구 해당 소지로 LEGAL-HOLD(미배선)이므로 증권 상품 설계 시 같은 쟁점을 먼저 검토해야 한다.
8. `gdc-pool.js`(법정화폐 <-> GDC 풀)는 LEGAL-HOLD로 전부 실패하도록 막혀 있어 법정화폐 충전·환율 교환
   시나리오는 시험할 수 없다. 사용자 간 환전 매칭(`src/gdc/currencyPool.js`)은 별도로 동작한다.
